# CHANGES 0.1.12-p0 — P0: memory-safe steady pipeline

Задание координатора (п. 1–9) по итогам аудита AUDIT-STEADY-0.1.11.md (ревизия 2, F15).
База: ValveBench 0.1.11 (нетронута, используется как эталон для сверки).

## Что изменено

### valvebench/pcm.py
* Новый блочный декодер `_decode_bytes_chunk()`: все временные массивы ограничены блоком
  `CHUNK_BYTES = 1 МиБ`; запрещённые полноразмерные int64-массивы (N,3) и цепочки промежуточных
  массивов больше не создаются нигде.
* `from_pcm()` сохраняет контракт (байты → float64 (n, ch)), но декодирует блоками. Для длинных
  capture использовать не его, а потоковые средства ниже.
* `raw_frame_count()`, `StreamPcmReader` (случайное чтение окон float64 без загрузки файла),
  `stream_to_float32_wav()` (один проход raw-PCM → float32 WAV IEEE-float, заголовок 44 байта,
  память ограничена блоком).

### valvebench/steady.py
* Capture-путь (бывш. строки 856–859): `read_bytes → from_pcm → astype(float32) → wavfile.write`
  заменён на `stream_to_float32_wav() → np.memmap(float32 WAV)`. Анализ читает окна из memmap.
* `_tone_continuity_track`: убрана упреждающая конвертация всего канала в float64 — окна
  конвертируются по мере чтения (числа те же).
* Хранение float32 точно для S24_3LE/S16_LE (мантисса 24 бита ≥ 23 бит сэмпла); для S32_LE
  появляется округление ~2⁻²⁵ FS (−150 dBFS) — задокументировано в docstring.

### valvebench/selftest.py
+ 2 проверки: `StreamPcmReader.read_frames == from_pcm` (включая границы блоков) и
  `stream_to_float32_wav` → scipy-читаемый float32 WAV с точными значениями. Selftest: **51/51 PASS**.

### Прочее
* `__version__ = "0.1.12-p0"`.
* Логика измерений, JSON, CSV, смысл метрик — без изменений.

Синтетический capture (тон 997 Гц −6 dBFS, шум −100 dBFS, broadband-burst, клик; расписание
production) прогонялся через зеркало пост-capture части `run_steady_test` (строки 856–919:
частоты состояний, channel map, `_analyse_channel` L/R, `_shared_excursion_stats`,
`_tone_continuity_track`):

* 192 кГц/30 с, 192 кГц/124 с, 176,4 кГц/124 с: **31/31 численных метрик равны побитово** в каждой
  паре (частоты состояний, channel map/crosstalk, baseline pre/post, residual med/p95/max/эпизоды,
  УЗ-полосы, carrier continuity, корреляции). Контроль 124 с: f_L = 997.0000015 Гц (истина
  997.0000000), baseline −103.84, max residual −54.81 (клик), 2 эпизода (burst+клик), 0 dropouts.

Независимый аудит-набор (34 проверки, включая production-тесты `from_pcm` на границах знака всех
форматов, интерливлинг, случайные байты, длинный поток, некратный буфер) против 0.1.12-p0:
**34/34 PASS**.

## Фактический peak RSS (п. 7 задания; /usr/bin/time -v, полный конвейер «загрузка + анализ»)

| Конвейер | 30 с @192к | 62 с @192к | 124 с @192к | 124 с @176,4к |
|---|---|---|---|---|
| 0.1.11 (old) | 674 МБ | 1286 МБ | **2420 МБ** | 2279 МБ |
| 0.1.12-p0 (new) | 252 МБ | 268 МБ | **361 МБ** | 343 МБ |

Рост old строго линеен по длительности (замерено на трёх длительностях), new — плоский
(остаточный рост — списки результатов анализа, не PCM). Декодер отдельно (124 с, only from_pcm,
по данным аудита): 1210/2208/2401 МБ при 96/176,4/192 кГц.

На машине с 7,1 ГиБ RAM полный прогон 192 кГц/124 с теперь требует ~0,36 ГиБ вместо ~2,4 ГиБ.
