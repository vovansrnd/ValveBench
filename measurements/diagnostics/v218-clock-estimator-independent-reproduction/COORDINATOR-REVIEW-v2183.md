## Executive decision

**v2.18.3 is a meaningful improvement, but is not accepted as a closed evidence package.** The new LSQ implementation now has an independent periodogram start, conditional single-stage decimation, and correctly scaled/bounded parabolic refinement. The saved MC rows record the real 48 kHz LSQ fit rate, and the summary statistics are broadly consistent with the per-trial batches. The white/colored model separation is retained, and the 1.85/4.30 s schedule arithmetic is still supported by the actual backend and Rig code.

However, the agent's 868 Hz reproduction uses the wrong historical estimator revision and therefore does not settle the exact v2.18.1 result. The pilot "measured profile" is hard-coded rather than reproducibly derived from source WAVs, and its PSD-to-sine amplitude conversion appears 3.01 dB low. The white noise floors are 3.01 dB higher than claimed when interpreted through the production `noise_dbfs` metric, and the verification does not measure those RMS floors. The schedule explanation still conflates two distinct 50 ms quantities. The resampling numeric script/JSON is still the invalid simultaneous-multitone experiment.

No production patch, main change, PR change, clock-gate change or pilot change is approved.

## 2. LSQ implementation — substantial fix accepted as a diagnostic candidate

`v2183_estimators.py` no longer uses the production centroid for its coarse start. It selects a Hann-window periodogram peak in ±2 Hz, conditionally decimates only when `fs > 96 kHz`, and returns the actual fit rate. At 48 kHz input the estimator now remains at 48 kHz. The RSS parabolic correction includes the missing `step` multiplier and bounds the correction to one grid interval. The spectral-peak parabola requires positive peak curvature and clamps fractional-bin correction to ±0.5 bin. These formulae are dimensionally consistent.

The original one-grid-step systematic shift is fixed in the committed implementation; reported LSQ bias is small in the saved model data. This is accepted as a leading **diagnostic** implementation, not yet as production code.

### Remaining acquisition-guard issue

The coarse peak is tested with `0 < k < len(X)-1`, not against the local search-band endpoints `ib[0]` and `ib[-1]`. If the strongest bin is at the edge of the ±2 Hz acquisition band, parabolic interpolation still uses the neighbouring global FFT bin outside that band. It can return a start near the search boundary, after which the ±0.15 Hz RSS refinement cannot reacquire the true tone. No explicit `acquisition_ok` / boundary status is returned.

The required strong-line test just outside the coarse interval is not reported as a deterministic boundary/invalid-acquisition test. The 997 Hz pilot is especially relevant: the 1000 Hz line is 3 Hz away, just outside a ±2 Hz search. Add a rule for a coarse peak on either acquisition-band boundary (expand/reject/mark invalid), and preserve the coarse-bin, neighbouring magnitudes, interpolated offset, fine-grid minimum and validity status per trial. Do not silently return a plausible ppm when acquisition may have locked to a sidelobe.

## 3. Blocking defect A — 868 Hz reproduction uses the wrong revision

The committed `v2183_868_reproduction.py` says it reproduces the function from commit `0b6853b`. That is the **older centroid-started estimator**: it calls `dsp.analyze_tone()`, starts at the production centroid and searches only ±0.05 Hz.

But the problematic v2.18.1 JSON was generated by `v2181_lsq_pilots.py` on the v2.18.1 branch, which imports the updated `est_lsq()` in commit `8d8b040969a9a872941ecfe502975f45419d4186`. That is a different function: independent periodogram coarse search over ±2 Hz followed by an **unbounded** coarse parabolic interpolation. It checks only a nonzero denominator; it does not require a concave local maximum or bound the parabolic offset. This is precisely the implementation whose output needs to be reproduced.

The v2.18.1 saved JSON for pilot 997 Hz / mains level −30 dBFS reports LSQ bias `−131878.593 ppm` under the old 1000 Hz reference formula. This corresponds to a mean estimated frequency of about **868.098 Hz**:
`1000 * (1 + (-131878.593 - 23.5)·1e-6) ≈ 868.098 Hz`.
The v2.18.3 reproduction of the older centroid-started `0b6853b` function returning ~1000 Hz does not refute that saved result.

Therefore the statements “868 Hz is impossible in any saved version” and “v2.18.1 JSON is stale” are **not established**. Rerun the exact v2.18.1 `est_lsq` from commit `8d8b040` (or an exact hash-identified copy), with the original `v2181_lsq_pilots.py` signal construction, seed formula and first 50 seeds. Save the coarse-bin index, three FFT magnitudes, denominator/curvature, parabolic offset (in bins and Hz), fine-search grid, selected minimum and returned frequency. Then repeat with the bounded v2.18.3 estimator. This is a mandatory close-out item.

## 4. White noise model — absolute levels are 3.01 dB above the claimed production metric

The production function `dsp.rms_dbfs(rms)` defines dBFS relative to a full-scale sine and computes `20·log10(rms·sqrt(2))`. The white generator instead sets standard deviation to `dbfs_to_amp(NOISE_*_DBFS) = 10^(dBFS/20)`, without dividing by `sqrt(2)`.

Consequently, when the generated Gaussian noise is evaluated with the same production `rms_dbfs` metric, the nominal levels are approximately **−77.0 dBFS and −93.0 dBFS**, not −80/−96 dBFS. To target the claimed production levels, the Gaussian standard deviations must be `10^(dBFS/20)/sqrt(2)`. Alternatively, relabel the model with the actual levels and rerun/recompute its documented SNR grid.

The current `verify_white()` only measures Pearson correlation. It does not measure channel RMS or production `noise_dbfs`, despite the agent's final message claiming both RMS levels were checked. Add measured per-channel RMS, `rms_dbfs`, and assertions against the intended floor. The correlation construction itself is mathematically consistent; the issue is the dBFS convention/verification.

The white MC remains useful as a synthetic white-noise comparison, but its absolute noise levels and any mapping to production during-tone floors are currently misstated by 3.01 dB.

## 5. Colored noise model — generator improved; verifier still incomplete

The v2.18.2 verifier's missing division by `n_check` is fixed. The saved PSD deviations are now approximately ±0.14 dB, which is consistent with the expected effect of smoothing the target PSD before synthesis.

However:
- the JSON stores synthesized gamma² and PSD deviations, but not the target gamma² values shown in the report; the five target numbers cannot be regenerated from this verifier artefact alone;
- it does not compare/save the complex cross-spectral phase, only magnitude-squared coherence. Matching auto-PSDs and gamma² magnitudes does not prove the full complex cross-PSD is reproduced;
- the coloured model is still constructed from quiet windows where D10 is idle and is not the during-tone noise/asymmetric channel condition. The report does disclose this limitation.

Save target and synthesized PSD, target and synthesized gamma², and complex cross-spectrum (magnitude and phase) for every verification band using one consistent CSD convention. Keep the model labelled “idle-window coloured floor”, not “realistic full during-tone tract”.

## 6. Pilot profile — corrected estimator and better test layout, but profile isn't reproducible yet

The pilot script's error is now computed relative to each tested pilot. It also has separate “measured” and uniform-comb stress modes, and its LSQ input remains at 48 kHz. The result that 997 Hz is more vulnerable to a nearby 1000 Hz line than 1013 Hz is plausible and useful as a diagnostic observation. The stress test also correctly demonstrates that a full-band LSQ can lose to a narrow-window centroid when strong unrelated lines are present.

But `v2183_pilots.py` does not read the source WAVs or accept `--source-dir`. The “measured” profile is a hard-coded `MEASURED_PROFILE_DBHZ` dictionary. The branch has no script that derives this 41-line vector from the source recordings, no per-line measured frequencies, and no source-window / estimator provenance. The manifest only lists seven capture WAVs, not the claimed 32 capture/program/THD files; the WAV payload itself remains excluded from Git.

There is also an amplitude-convention issue. The script converts one-sided Welch PSD into a sine peak amplitude using `sqrt(PSD * 23.4)`. Welch's one-sided PSD integrates to mean-square power; `dbfs_to_amp()` is a peak-amplitude scale and the signal is added as `amp·sin()`. To convert integrated line mean-square power to sine peak amplitude, the factor is `sqrt(2·P_line)`, not `sqrt(P_line)`. The current line amplitudes therefore appear about **3.01 dB too low**, unless the stored dictionary was already peak-normalized by a separate undocumented process. That normalization needs to be shown and verified.

Required: create a reproducible extraction script using the source captures/quiet windows. Estimate each harmonic's actual frequency and integrated line power (not a single PSD bin times nominal bin width), preserve the full per-line vector and source hashes in JSON, convert RMS line power to peak sine amplitude correctly, and rerun 997/1000/1013. Replace Python's process-randomized `hash((mode, mains_level))` seed construction with a stable explicit integer mapping; save both pilot-script and estimator-module SHA256 values. Keep the flat comb strictly as a stress case.

Do not change the production 1 kHz pilot yet. The data suggest a real tradeoff: 997 may suit the narrow-window centroid, while 1013 may suit LSQ. A single winner has not been established.

## 7. Schedule — correct numerical timeline, remaining 50 ms naming error

Production code confirms:
- `backend.play_record()` starts arecord, waits 0.30 s, and prepends a 50 ms **backend leading pad** to the playback data;
- `Rig.run()` with edge protection prepends a 1.5 s lead;
- `Rig._seg()` contains 0.4 s of tone before the 2 s analysis window and adds a distinct 50 ms **segment tail reserve**;
- `backend.play_record()` also appends its own trailing 50 ms pad after the whole programme.

Thus expected tone start is `0.30 + 0.05 backend-leading-pad + 1.50 edge-lead = 1.85 s`. Expected tone end is `1.85 + 0.40 settle + 2.00 analysis + 0.05 _seg tail reserve = 4.30 s`. The separate backend trailing pad follows the programme and does not extend the tone.

The v2.18.3 report still says the 0.05 pad is the `_seg` tail reserve and “not a leading element”, but the 0.05 used in the start calculation is actually the **backend leading pad**. There are two distinct 50 ms quantities. Correct the diagnostic script/report labels; retain 1.85/4.30 and the +375 ms observed capture-1 late start. The process-launch vs first-recorded-sample caveat and unknown physical mechanism remain.

The production window's +350 ms overrun is still calculated from hard-coded per-capture `prod_onset` values; treat it as cross-check, not independent detector reconstruction.

## Architecture direction

The v2.18.3 results strengthen the case for **per-channel LSQ with explicit acquisition validity, uncertainty, tone presence, SNR and window-validity QC**. But the pilot stress tests also show that full-band LSQ can be much worse than a narrow-window centroid when a strong neighbouring line is present. The production estimator should not blindly prefer LSQ: it needs a line-contamination/acquisition-quality gate, or a nuisance-line-aware fit, and should retain centroid as a separately qualified fallback rather than averaging unconditionally. Validate this in diagnostics before implementation.
