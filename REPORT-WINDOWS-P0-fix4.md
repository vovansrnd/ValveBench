# Отчёт: P0 «два окна» — fix4. Причина, исправление, доказательства

Дата: 09.11.2026. Задание координатора/аудитора: исправить повторное создание
окон ValveBench, предоставить тест многократного activate, проверить конфликты
копий с одинаковым application_id, оформить отдельной версией (fix3 не тронут).

## 1. Диагноз (подтверждён воспроизведением)

* `GApplication` с `application_id="local.valvebench"` — один экземпляр на
  сессию D-Bus. Повторный `./run.sh` завершается, переслав `activate`
  работающему процессу.
* Обработчик `lambda a: Window(a).present()` создавал новое окно на каждый
  сигнал. Итог: второй запуск → 2 окна, третий → 3.

Воспроизведение ДО исправления (изолированный стенд: собственный D-Bus через
dbus-run-session + собственный Xvfb, окна считает xwininfo; реальные запуски
`./run.sh` — `verification/test_single_window_e2e.sh`):

| Сценарий | Окон |
|---|---|
| 1-й запуск | 1 |
| повторный ./run.sh (второй процесс завершился: remote-активация) | **2** |
| третий запуск | **3** |
| закрыть всё → новый запуск | 1 |

Лог стенда: «второй процесс: завершился (remote-активация первичного)» —
ровно механизм, предсказанный аудитором.

## 2. Исправление (valvebench/ui.py, класс App)

По схеме аудитора: `self._window`; первое activate — создать, повторные —
только `present()`; `close-request` сбрасывает ссылку и возвращает False.
Обработчик `Window.on_close` (stop_live, analysis.close, сохранение
калибровки/настроек) не тронут — подключается раньше и выполняется полностью.
Диф: `verification/fix3-to-fix4-ui-app-singlewindow.patch` (39 строк).

### 3.4 Инструментальный пробник

`gui_live_probe.py` подключал СВОЙ activate-хендлер рядом с лямбдой App — оба
создавали окно: при профилировании на рабочем столе появлялись два окна за
один запуск пробника. Это моя ошибка измерительного скрипта (и она же маскировала
дефект продукта как «свойство»); пробник переведён на ожидание окна App
(`app._window`). Проверен прогоном под Xvfb: одно окно, самозавершение.

## 4. Конфликты копий с одинаковым application_id (проверка аудитора)

* Сейчас ValveBench в системе не запущен (pgrep — пусто; фиксировали PID/cmdline/cwd
  на стенде: первичный `/usr/bin/python3 -m valvebench` из дерева запуска).
* В системе **27 копий** ValveBench (от 0.1.2 до dev3, включая установленную
  `/opt/MyApps/Adudio/ValveBench` и git-версию) — ВСЕ с одним
  `application_id="local.valvebench"`. Пока живёт любая старая копия, запуск
  dev-копии активирует СТАРУЮ (и наоборот): пользователь попадает не в ту
  версию, которую запускал. С fix4 это уже не плодит окна (старая копия без
  fix4 по-прежнему будет плодить СВОИ окна — защищает только исправленная
  сторона).
* Настройки (`~/.config/valvebench/ui.json`, калибровка, оверлеи) хранятся в
  JSON и от application_id не зависят — технических препятствий для смены id нет.
* Решение за координатором, варианты:
  1. Оставить один id — повторные запуски любой копии показывают уже открытое
     окно (с fix4 безопасно), но версия «по клику» может быть не та, что ждала.
  2. Версионировать id (например, `local.valvebench-0.1.20`) — каждая копия
     самостоятельна; потребуется синхронизировать .desktop-файлы пользователя.

## 5. Признанные замечания аудитора к предыдущему отчёту (без спора)

1. **«Скрытые страницы не выполняют вычислений» — формулировка была неполной.**
   Точно так: AnalysisWorker-процесс останавливается (0.2% CPU при скрытых
   спектре/peak hold), но GainTracker в LivePage.tick продолжает расчёты на
   ЛЮБОЙ видимой странице (~30% ядра при включённом генераторе): тик кормит
   индикаторы шапки (уровни + ΔG), которые видны всегда. Кандидат №1 для
   0.1.21: на скрытой странице Gain Match — сниженный темп тика (например,
   300 мс вместо 75) без изменения математики; оценочная экономия ~20–25%
   ядра в состояниях S4–S6.
2. **250 мс худший провал событийного цикла** — отзывчивость UI не может
   считаться принятой только по нулевым XRUN. Провалы наблюдаются на
   переключении страниц (первый кадр тяжёлой страницы) и не воспроизводятся
   в стационаре (p95 = 44.5 мс). В бэклог 0.1.21: инструментальная проверка
   провала (кадровая статистика + профилирование первого кадра страницы).
3. Аппаратный этап (E-MU) приостановлен по указанию координатора до
   стабилизации одиночного окна; прогон приёмки GUI выполнен на ASUS DLX
   (fallback-карта, та же кодовая дорога AlsaCli).

## 5а. fix4.1 — изоляция application_id (P0.1, по дополнению координатора)

Реализовано ровно по заданию: dev-копии получают детерминированный
`local.valvebench.dev.p<12 hex SHA-256(realpath)>`, установленная копия
(без `verification/`) сохраняет `local.valvebench`, `VALVEBENCH_APPLICATION_ID`
переопределяет всё. Полная последовательность координатора A→A→B→B→A→закрыть-A
пройдена E2E в одной D-Bus-сессии: **18 PASS / 0 FAIL**
(`test_dev_ids_e2e.sh`, вердикт: /tmp/dev-ids-verdict.txt) — запуск B поднимает
ИМЕННО B (живой процесс, своё окно, свой id на шине), повторные запуски не
плодят окон, повторная активация A показывает существующее окно A.

Побочная находка при отладке: GDK внутри проверочных Xvfb-сессий может уходить
на Wayland пользователя (сокет wayland-0 в унаследованном XDG_RUNTIME_DIR) —
окна тестов тогда появляются на рабочем столе пользователя. Оба E2E-стенда
теперь подменяют XDG_RUNTIME_DIR и фиксируют GDK_BACKEND=x11: тесты полностью
изолированы от твоей сессии. (Это же объясняет, почему окна моих прошлых
проверок иногда выглядели «на твоём столе».)

Архив: `ValveBench-0.1.20-dev3-reviewfix4.1-singlewindow.tar.gz`
(SHA256 в `.sha256` рядом); архивы fix3 и fix4 сохранены без изменений.
